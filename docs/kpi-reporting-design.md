# Reports & Analytics — KPI Technical Design

**Milestone 1 deliverable.** The client confirmed 5 KPIs for the Phase 1 Reports & Analytics dashboard (`PROJECT_TRACKER.md` Section 4). This document maps each one to the actual data model (`app/api/prisma/schema.prisma`) so the Milestone 5 dashboard build has a concrete query plan rather than starting from scratch. No dashboard UI is built yet — this is the design only, as scoped for Milestone 1.

## 1. Total number of members

Straightforward count against `Member`, optionally broken down by `membershipStatus` (a "total" figure should almost certainly mean `ACTIVE` members, with `EXPIRED`/`CANCELLED` shown separately rather than folded in — worth confirming with the client which one they mean by "total" before building the dashboard).

```sql
SELECT "membershipStatus", count(*) FROM "Member" GROUP BY "membershipStatus";
```

Fully buildable today — no dependency on Milestone 4 data.

## 2. Breakdown between Founding / Annual / Newsletter

Same table, grouped by `membershipTier`. Two things worth flagging now, before this gets built:

- The tier enum now also includes `MONGOLIA` (added 2026-09-01, see Section 3a) — the dashboard's breakdown should show whichever tiers actually exist by then rather than hardcoding the original 3, so it doesn't need a code change if a 5th tier is ever added.
- `isFoundingMember` is a separate, permanent flag (survives even if the paid term lapses) — the "Founding" segment of this KPI should almost certainly be `isFoundingMember = true` count, not `membershipTier = 'FOUNDING'` count, since a Founding Member's `membershipTier` could theoretically diverge from their permanent badge later. Worth confirming this distinction is what the client has in mind.

```sql
SELECT "membershipTier", count(*) FROM "Member" GROUP BY "membershipTier";
SELECT count(*) FROM "Member" WHERE "isFoundingMember" = true;
```

Fully buildable today.

## 3. New members per period

`Member.createdAt`, bucketed by whatever period the dashboard offers (day/week/month). Standard time-series query, no new schema needed.

```sql
SELECT date_trunc('week', "createdAt") AS period, count(*)
FROM "Member" GROUP BY period ORDER BY period;
```

Fully buildable today.

## 4. Sales/orders generated by members

This is the one KPI genuinely blocked on other work: `MemberOrderCache` already exists in the schema (order id, order number, total amount, currency, status, order date — see `GET /members/me/orders`, built 2026-09-01), but it's populated by a Shopify order-sync webhook that hasn't been built yet (Milestone 4). Until then, this table is empty for every member and this KPI has no real data to show.

Once the sync exists, the query itself is simple:

```sql
SELECT sum("totalAmount"), count(*) FROM "MemberOrderCache"
WHERE "orderDate" BETWEEN :start AND :end;
```

**Not buildable until Milestone 4's order sync exists.** Flagging this now so it isn't a surprise when Milestone 5's dashboard work starts.

## 5. Member activity/engagement

This is the one KPI without an obvious data source yet, and needs a scope conversation with the client before it can be designed properly — "activity/engagement" could mean several different things depending on intent:

- **Login frequency** — buildable today if we start recording a `lastLoginAt` timestamp on `Member` (currently not tracked — every login just upserts contact fields, doesn't record the event). Small additive schema change whenever this gets prioritized.
- **Portal usage** (which pages/features members actually use) — would need real usage-event logging, which doesn't exist and wasn't scoped as a requirement anywhere else in the project. This is a bigger addition than a single field — worth clarifying with the client whether they actually want this level of tracking (it also has GDPR/data-minimisation implications worth being deliberate about, given Section 4's "portal DB stores only membership-specific fields" principle).
- **Order/purchase activity** — would overlap with KPI 4 above, same Milestone 4 dependency.

**Recommendation:** don't guess at this one. Suggest asking the client what "engagement" specifically means to them (login frequency is the cheapest, lowest-risk interpretation and covers the common case) before Milestone 5 designs the dashboard around the wrong definition.

## Summary for planning purposes

| KPI | Buildable today? | Blocker |
|---|---|---|
| 1. Total members | Yes | — |
| 2. Tier breakdown | Yes | — |
| 3. New members per period | Yes | — |
| 4. Sales/orders by members | No | Milestone 4 order-sync webhook |
| 5. Member activity/engagement | No | Needs client clarification on definition, then possibly a small schema addition (`lastLoginAt`) |

Three of the five KPIs need no new backend work when Milestone 5 starts — just dashboard UI querying data that already exists. The other two have real, identified dependencies rather than being open-ended unknowns.
